---

## 1. What we are building

**TrustFed-SDN** is a federated learning (FL) framework for **cross-tenant threat detection** in SDN-enabled multi-tenant cloud networks. Each tenant keeps its traffic private, trains a local detection model, and shares only protected model updates. The framework adds four protections on top of plain FedAvg and validates everything on a real SDN testbed:

| Pillar | Meaning | Where it lives |
|---|---|---|
| Real SDN testbed | Mininet + Open vSwitch + RYU, tenants as isolated domains (attack / benign / victim machines per tenant) | `testbed/` |
| Adaptive per-tenant DP | Privacy budget allocated per tenant from a sensitivity score, instead of one uniform noise level | `trustfed/privacy/` |
| Verifiable secure aggregation | Updates are masked and committed; tenants can check the aggregate was computed correctly (value-level integrity) | `trustfed/verify/`, `trustfed/aggregation/` |
| Poisoning-robust aggregation | Coordinate-wise trimmed mean and similarity clustering filter malicious updates | `trustfed/aggregation/` |

**Local model:** GRU (justified by a small ablation against DNN and LSTM in Step 02).
**Datasets:** InSDN (primary, SDN-native), CICIDS2017 (supplementary), CICDDoS2019 (optional), plus a **live dataset generated on our own testbed** (Step 07).
**Research claim to test (not to assume):** the combination of real SDN validation + verifiability + poisoning robustness + adaptive DP is not available in prior work, and its cost is acceptable.

## 2. What the finished project contains (expected output)

1. **Core library** `trustfed/` with unit tests: data pipeline, GRU/DNN/LSTM models, FedAvg, robust aggregators, DP module, masking + commitment + verification, metrics.
2. **Simulation suite** `sim/`: dataset-driven FL experiments with N tenants, non-IID partitions, attacks, and sweeps, all driven by YAML configs.
3. **Live SDN testbed** `testbed/`: multi-tenant Mininet + OVS + RYU topology, per-tenant RYU apps (flow statistics, feature extraction, policy enforcement, model deployment), attack and benign traffic generators, optional real-VM layer.
4. **Live FL pipeline** running across tenants on the testbed, with the global model deployed back to each tenant controller for real-time detection and mitigation.
5. **Complete experiment results** in `results/` (CSV/JSON), with figures in `figures/` and LaTeX tables in `tables/`, all generated by one command (`make reproduce`).
6. **Ablation ladder:** FedAvg → +DP → +Robust Aggregation → +Verifiable Aggregation → Full TrustFed-SDN.
7. **Project website** in `site/`, deployable at `https://trustfed.naimurrashid.dev/` (the address already printed as a QR code on the poster).
8. **Documentation:** architecture, reproducibility guide, experiment spec, deviations log, and a short "results summary" file that thesis and poster text can be copied from.

1. The user says: "Read AGENTS.md and PROJECT_PLAN.md, then start Step N."
2. The agent reads the step file, asks the "Ask the user first" questions in small batches, then posts a short plan.
3. The user replies "go" (or corrects the plan).
4. The agent implements, tests, commits, and posts the step report.
5. The user reviews and replies "approved step N" or requests changes.
6. The agent tags `step-NN-done`, updates `PROGRESS.md`, records all empirical results/metrics in `docs/EXPERIMENT_RESULTS_LOG.md` (formatted for paper writing), and proposes the next step (without starting it).

Data downloads follow `docs/DATASETS.md`: the agent tells the user exactly what to download and where to put it, or downloads it after asking permission.

## 6. Design decisions that need the user (and ideally the supervisor)

| Topic | Step | Why it matters |
|---|---|---|
| Isolation level of the testbed: L1 Mininet namespaces, L2 containers, L3 real VMs | 07 | The poster says tenants are VMs. L3 needs a lot of RAM and CPU. A mixed setup (L3 for a subset of tenants, L1 for the rest) may be the practical choice and must be stated honestly in the thesis. |
| DP granularity (record-level DP-SGD vs update-level noise) and the budget policy across tenants | 05 | Defines what the privacy guarantee actually means. The poster formula splits a total budget by inverse sensitivity; the agent must document exactly what that implies. |
| Verification scheme: homomorphic hash / commitments vs keyed linear checksum | 06 | Different security assumptions and costs. A plain hash of a masked update alone does not prove the aggregate is correct. |
| Tenant sensitivity score definition | 05 | Drives the adaptive part of the novelty claim. |
| Local model choice | 02 | Decided by evidence from the ablation, not by assumption. |

## 7. Expected results are hypotheses, not facts

The poster lists targets. They must be **tested**, and the real numbers must be reported even when they miss:

| Aspect | Target from the poster |
|---|---|
| Detection | Comparable to the centralized baseline; above plain FedAvg under attack |
| Communication overhead | About 1.2–1.5× plain FedAvg, decomposed into commitment, mask, and DP-noise cost |
| Robustness | Accuracy drop below 5 points at 20% poisoned tenants (versus above 15 points for plain FedAvg) |
| Privacy | Membership-inference success close to random (about 50–55%) with adaptive DP |

Numbers from other papers (for example 99.96% on CICIDS2019 or 98.85% on CAIDA) used different datasets and setups. Compare against them only as context, never as a direct benchmark, unless the same dataset and protocol are reproduced.

## 8. Risks and fallbacks

| Risk | Fallback |
|---|---|
| The user's computer is Windows | Run the testbed inside an Ubuntu 22.04 or 24.04 virtual machine (or a separate Linux machine). Algorithm steps (01–06) can run anywhere with Python. |
| Not enough RAM for many real VMs | Use L3 for one or two tenants only (for example 3 VMs per tenant), and L1/L2 for the rest. Document it. |
| RYU incompatibility with newer Python versions | Pin a compatible Python and `eventlet` version for the RYU environment (verify in Step 00), or use a maintained fork. Keep the ML environment separate from the RYU environment. |
| Live traffic features differ from dataset features | Select features that the live extractor can reproduce (see Step 07), and report the feature set honestly. |
| No GPU | The models are small tabular models. CPU training is acceptable. |
| Large dataset downloads fail | Use the manual download instructions in `docs/DATASETS.md`. Start with InSDN only. |
| Time pressure | Primary track: Steps 00–05, 07, 08, 09. Secondary track items (Step 06 advanced options, CICDDoS2019, extra aggregators) can be reduced, but must be listed as limitations. |
